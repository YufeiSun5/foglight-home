设计依据：2026-10-06 初始化方案及作者后续实施指令。以下是设计契约与明确标注的待验证建议，不是实现或验收完成记录；当前工作及待确认事项统一见 [AI_BOARD](../../AI_BOARD.md)。

来源：《雾灯归航_技术架构与模块设计_v0.1》2026年10月6日最新8页修订版，合入同日获批的 AI 协作初始化方案。本文是技术选型、分层契约、状态数据、存档与测试设计的唯一技术母本；不平行维护另一套架构。云端执行、画面、玩法与衣装的上位硬约束见[唯一母本](../instructions/execution-and-visual-constraints.md)，文档维护与实现检查方法见[核验约定](../instructions/verification.md)。

叙事入口：[八章纲要与呈现约定](../../docs/narrative/outline.md)、[人物与动作](../../docs/narrative/characters.md)、[第一章台本](../../docs/narrative/scripts/chapter-01.md)、[后续关键场景](../../docs/narrative/scripts/key-scenes.md)。剧情、身体体验与婚姻关系以对应叙事文件为准，技术模型只记录经确认的剧情事实。

*供项目立项与第一章原型使用  可编辑设计稿*

设计基线采用 Godot 4.6.x、GDScript 与 Blender，以高细节材质的真实3D海港环境承载精致2D像素人物和联动半身对话立绘；Windows PC 首验、离线单人、预编写剧情，一个雾港关卡三个分区、四位暂定成人角色、10–15分钟首章。先验证一位角色与一处海港小景，再扩展首章。产品实现已获授权，效果仍须按门禁验证；成年假设仍待作者确认。主要体验为自由交谈、故事探索，轻量 roguelite 路线/事件/临时增益可选；原强制解谜方案作废。

## 1 推荐技术组合

| 部分 | 建议 | 选择理由 |
| --- | --- | --- |
| 游戏与脚本 | Godot 4.6.x + GDScript | 原生3D场景与精灵节点；小原型便于集中管理代码、动画和UI |
| PC画面 | Forward+；固定或有限转动镜头 | 适合体积雾、发光与丰富动态光影；先控制人物方向素材规模 |
| 美术制作 | Blender + 2D修整工具 | 环境输出GLB；角色可预渲染为精灵帧，再统一像素风格 |
| 叙事与存档 | 本地JSON定义 + 独立状态服务 | 剧情可审阅、校验、回放；第一版无需在线服务 |
| 版本管理 | 当前公开 Git 仓库；大资产按需评估 Git LFS | 小步提交、频繁合并；原始私人材料不入库，大资产先核许可和额度 |

Unity + C# + URP也是可行备选，适合已有Unity资产与工作流的团队。当前没有必须转向Unity的需求，Godot具备适合本项目的功能与许可基础，建议集中一条管线。Unity的许可资格和订阅规则应在实际采用前核查。[1][2][10]

## 2 分层架构与模块契约

采用 **单个 Godot 工程内的模块化单体**。探索、剧情、可选短途事件、关系和存档在一个进程内协作，用明确的数据与状态边界控制复杂度。

首章规模不需要 HTTP 后端、服务数据库或游戏运行时 MCP。离线单人状态用版本化本地文件持久化；剧情定义与美术资源跟随构建。AI 开发协作工具与游戏运行架构分开，工具的存在不应变成玩家运行游戏的依赖。

只为持久化、资源加载等真实外部边界建立可替换契约，以便模拟失败和无图形测试。领域内部采用普通类型、函数和小模块，不为每个任务、角色或规则强造接口、容器或通用事件总线。

### 分层契约与状态权威

下表是已批准的设计契约。路径是模块的计划落位；是否已存在及已验证以 AI_BOARD 与对应远端代码为准。表中的测试为实现验收要求，文档自洽检查不能代替运行证据。

| 层与计划路径 | 职责与禁责 | 公开输入 → 输出 | 允许／禁止源码依赖 | 状态权威与验证 |
| --- | --- | --- | --- | --- |
| 展示与场景 `src/presentation/`、`scenes/` | 移动表现、交互检测、对白 UI、镜头、动画、音频；不得直接改剧情状态、发奖励或读写存档 | 玩家意图、只读视图、已提交事件 → 用例请求、带代次的演出回执 | 可依赖应用层公开 API；不得引用存档适配器或领域写入口 | 只拥有局部物理运动、显示缓存、焦点和动画状态；存档锚点经应用提交；检查重绘无副作用、旧回执被拒绝 |
| 应用流程 `src/app/` | 统一处理选择、交互、可选短途事件、场景切换与读档；持有输入锁、取消令牌和 StateStore；不得包含渲染细节 | 带 ID／修订号／会话代次的命令 → CommitResult、只读快照、已提交事件 | 可依赖领域层和自身边界契约；不得引用具体场景或文件适配器 | StateStore 为剧情／故事记录／库存／衣装／关系及恢复锚点的唯一写入口；测试整批提交、幂等、锁释放 |
| 领域规则 `src/domain/` | 剧情条件、故事记录、可选路线/事件/临时增益、关系事实、边界／同意、故事时钟与库存不变量；不得访问节点树、文件或 UI | 已验证定义、状态值、命令 → 候选新状态、效果、拒绝原因 | 可依赖领域内纯模块／值类型；不得依赖应用、展示、适配器 | 规则定义有效状态，不能私藏第二份可变全局状态；测试纯计算与回放 |
| 外部边界 `src/app/ports/` | 最小 SavePort、ContentPort／SceneLoaderPort 契约；不得把所有内部调用抽象成接口 | SaveSnapshot、槽位、资源 ID → 明确成功／失败结果 | 仅依赖所需值类型；不得依赖具体 IO 实现 | 不持有权威状态；用测试替身注入磁盘、资源与加载失败 |
| 适配器 `src/adapters/` | 内容解析、版本迁移、文件持久化、引擎资源加载；不得决定剧情奖励或擅改关系 | 边界请求 → 经校验数据、持久化回执、可恢复错误 | 可依赖边界契约及共享值类型；不得绕过应用用例回写状态 | 存档是已提交状态的持久化副本；检查损坏、迁移与中断恢复 |
| 内容与资产 `content/`、`assets/`、`art_source/` | 稳定 ID、条件／效果白名单、文本和资产；不得嵌入任意脚本表达式 | JSON／资源清单 → 经验证定义 | 数据引用已声明 ID；不得用节点路径或脚本名充当剧情语义 ID | 定义是只读内容，运行状态另存；检查 ID、引用、出口与资产许可 |
| 装配入口 `src/bootstrap/` | 建立依赖、启动服务、注入适配器；不得堆积游戏规则 | 启动配置 → 可用 GameRoot 或可操作错误菜单 | 可引用各层进行装配；其他层不得反向依赖它 | 不另存剧情状态；验证启动失败不会留下半初始化世界 |

**源码依赖不是运行调用顺序。** 例如应用在运行时调用 SavePort，实际执行适配器，但应用源码不引用该适配器；启动入口负责注入。信号从状态提交回到 UI，也不允许领域层反向引用 UI。代码审查同时查显式 preload／load、class_name 类型引用、场景脚本引用和动态加载路径。

**统一命令契约**：含 `command_id`、`source_id`、`expected_revision`、`session_epoch`、交互实例令牌与 payload。当前会话内相同 ID 和相同请求的已提交重试返回原结果，不重新执行效果；同 ID 不同载荷拒绝，旧会话回调拒绝。只有未提交的新命令继续验证当前节点、选项、条件和权限，不能信任 UI 的可见状态。

一次成功提交才推进 revision 并发布事实事件。幂等账本和剧情状态一同保存；效果按“逻辑发生实例”去重，避免把不同短途轮次的同类事件误当成永远只能发生一次。向展示层返回不可变值或隔离副本，不泄露可修改的内部 Dictionary／Array。加载新游戏或存档更换会话代次；切换场景或对话更换交互代次，旧回调只能被丢弃。

### 模块落位与审查要点

- GameFlow、Story/Dialogue 用例与 StateStore 归应用层；GameFlow 协调探索、对白、演出、过场与暂停，StateStore 处理命令与提交。二者不持有重复的剧情事实
- World/Interaction 与 Presentation 归展示层：移动、碰撞、交互检测、相机、动画、音频和 UI 只产生意图或表现已提交结果
- StoryProgress、OptionalRun、Appearance、Relationship、StoryClock 与条件计算归领域层；其结果先形成候选状态，经应用统一提交，不能由信号监听者直接结算
- Save/Content 的契约归应用边界，持久化、解析、迁移与资源加载实现归适配器；启动装配归 bootstrap
- 所有事件携带 event_id、revision、kind、稳定对象 ID；不携带易失效节点引用。消费者记录已处理 event_id；场景重载以只读快照重绘。直接返回值用于一次请求，信号只通知已提交事实，不以无约束全局信号链推进任务

## 3 叙事数据与状态模型

定义文件描述规则与内容，存档保存本次游玩的状态。定义使用长期稳定的英文ID，显示文本使用本地化key；改中文名称不应破坏引用。下面是设计样例，不是可运行游戏代码。

| 实体 | 定义字段 | 运行状态与约束 |
| --- | --- | --- |
| Character | id、display_name_key、成年年龄、portrait、animation_set | 岑星遥26、沈砚舟32、许知微33、祁岚29；称谓来自已确认关系 |
| DialogueNode | id、speaker、text_key、conditions、choices、effects、next | active_node、选择历史、恢复锚点；next必须存在 |
| StoryProgress | id、scene_ids、recordable_facts | 记录已观看/跳过的故事演出，不作为强制任务；逻辑效果只提交一次 |
| OptionalRun | id、route_pool、event_pool、temporary_boons | 自愿开始/退出的短途轮次；临时增益与持久剧情分离，失败不清除剧情、关系或衣装 |
| Appearance | character_id、outfit_id、top_id、top_color、outerwear_id、outerwear_color、bottom_id | 所有固定皮肤开局即用；世界角色、半身立绘和衣柜读取同一只读衣装视图；下装仅需全身/衣柜显示 |
| Relationship | pair_id、可记录事实类型、边界范围 | 信任以叙事事实记录；boundary与consent独立、可撤回、有情境 |
| StoryTime | chapter_id、day_index、time_slot、advance_rules | 只在获准剧情节点跳转；对话停顿或现实离线不推时间 |
| World与Inventory | 场景ID、交互物ID、道具定义、触发条件 | 物体状态、唯一道具实例、已完成触发器；保存可选交互与故事触发事实；不保存节点路径 |

### 船舱表达选择的节选样例

```json
{
  "id": "CH01_S04_CABIN",
  "speaker": "shen_yanzhou",
  "text_key": "ch01.terms.prompt",
  "choices": [{
    "id": "CH01_C02_TERMS.private", "text_key": "ch01.terms.private",
    "conditions": [{"fact": "harbor_arrival", "equals": true}],
    "effects": [{"kind": "record_choice",
      "choice_group": "CH01_C02_TERMS",
      "value": "not_explaining_private_history"}],
    "next": "CH01_S05_DEPART"
  }]
}
```

condition与effect只允许命名白名单操作，不执行嵌入脚本或任意表达式。内容检查需发现重复ID、悬空引用、无出口节点、不可达剧情、缺翻译和非法效果。故事记录、短途轮次与关系事实使用不同命名空间。

appearance_stage仅记录剧情演出阶段，不能限制outfit_id；玩家自选衣装状态独立保存且不被故事赠衣或时间跳转覆盖，不增加好感或能力。上衣少款多换色、下装多选项；服饰资源映射至同一衣装视图，半身立绘同步上衣/外套颜色，无需重复绘制下装。起点flags记录女主已获HRT认可与配给、家人反对；不能改写成等待第一次批准。是否已实际开始用药尚未明确，不由系统推定。

角色的HRT经历和身体决定只作为人物叙事及自愿披露内容；不设胸围、剂量、手术进度数值，不把治疗或手术设置为恋爱解锁条件。角色边界被尊重是关系设计的一部分，信任也不能替代一次具体同意。

## 4 分支执行与可靠存档

### A 玩家对话选择到一次性效果

1. 应用发出带交互实例令牌和 revision 的对白视图。玩家选择后 UI 禁用重复输入，但 UI 禁用只防误触，不能替代应用校验。
2. 所有选择进入同一个用例。先检查请求结构与当前会话代次，再核对幂等账本：同 ID 同指纹的已提交请求直接返回原结果，不重新检查已被该提交推进的 revision 或交互节点；同 ID 不同载荷拒绝。未提交的新命令才校验交互代次、当前节点、选项可用性及 expected_revision。同一交互即使用不同 command_id 双击，也只能消费一次选项令牌。
3. 领域规则在候选状态上计算故事记录、短途轮次、衣装、库存、关系与故事时间效果；全部有效才由 StateStore 原子提交。任何一项失败，整批状态与 revision 均保持不变。
4. 返回明确结果并发布已提交事件。UI、灯光和动画据此重绘；跳过或重播演出不会再次结算效果。失败反馈保留可重试入口，已提交选择不会因演出失败回滚重发。

### B 场景转换到可靠自动存档

1. GameFlow 接受一次转换请求，取得输入锁与转换代次，等待当前状态事务完成。先冻结离开场景的稳定快照与恢复锚点，写入请求携带 session_epoch、revision 与每槽独立递增的 write_sequence；write_sequence 随存档元数据保留，不能用会因读旧档或新游戏而回退的剧情 revision 充当跨会话写入顺序。
2. 快照包含 schema_version、content_version、构建号、稳定场景／出生点 ID、剧情状态、幂等账本与校验值；不序列化活节点、临时动画位置或 NodePath。
3. 经单写入队列，按槽位 write_sequence 防止旧写入覆盖新快照，同会话内另查 revision 不倒退；排队时与正式槽替换前均校验 session_epoch，过期会话的请求不得落槽。在正式槽同目录写临时文件；完成写入和可用的刷新，再回读、解析、检查校验值及状态引用。保全上一有效备份后，使用目标平台已验证的原子替换方案更新正式槽。
4. 只有正式槽替换成功且最终读取验证对应 revision，才回报“保存成功”。排队成功、临时文件写完、动画播放结束都不算持久化成功；不能把普通 flush 宣称为断电零丢失保证。
5. 离场保存成功后加载目标场景，重建碰撞／角色并应用快照；目标稳定后提交新场景锚点，再请求自动保存。若第二次保存失败，提示尚未保存并保留离场槽，读档回到原稳定锚点。首章仅分区镜头切换时复用同一协调规则，不必卸载整个雾港。
6. 离场保存失败则留在原场景并提供重试／取消；加载失败回到可操作的原场景或菜单。所有出口释放输入锁并作废旧回调。读档先在临时对象中完整校验／迁移，成功后先在保存队列设置屏障，取消未开始的旧请求并等在途写入结束，再提升 session_epoch 并替换活动状态；新游戏沿用同一屏障规则。损坏或更高版本存档不覆盖原槽，允许恢复已验证备份。

### 存档外壳与版本策略

```json
{
  "schema_version": 1, "content_version": "prototype-0.1",
  "slot_id": "manual_01", "revision": 42,
  "checkpoint_id": "CH01_S04_CABIN",
  "story_time": {"chapter_id": "CH01", "day_index": 1,
                 "time_slot": "evening"},
  "world": {"scene_id": "FOG_HARBOR", "spawn_id": "CABIN"},
  "story_progress": {"Q01_RELIGHT": {"seen_scenes": ["CH01_S01_GATE"],
                     "skipped_scenes": []}},
  "optional_run": null, "appearance": {},
  "relationships": {}, "inventory": [],
  "flags": {}, "applied_command_ids": [], "applied_effect_ids": []
}
```

实际存档另带保存时间、游戏构建号与校验值；示例空对象仅表示字段形状；applied_command_ids 不能代替请求指纹与原结果账本，实现还须按第2节统一命令契约持久化这些信息，并校验同 ID 不同载荷。设置独立保存，不把按键配置、字幕大小等混进剧情迁移。校验值用于识别损坏，不提供加密或防作弊保证。

### 槽位与恢复补充

写入及切换的唯一完整协议见本节流程 B；不能将下列槽位建议解释成另一套保存流程。各目标系统的原子替换与崩溃恢复必须实测。

建议3个手动槽与轮换自动槽。读取顺序：大小与格式检查、schema迁移、content引用检查、状态规则检查，再交给场景恢复。遇到更高版本存档拒绝覆盖；迁移失败提供备份恢复。删除或改名内容ID须提供映射，不能静默丢掉玩家选择。

幂等记录必须随存档保存。原型可保留全部已执行ID；全游戏仅在有证明不会重入的检查点做压缩。八章数月旅程由章节跳转驱动，游戏不模拟医学变化，也不因玩家晚几天回来而错失关系情节。

### 第一章流程与场景切换

首章故事演出顺序为 CH01_S01_GATE → CH01_S02_MEET → CH01_S03_REPAIR → CH01_S04_CABIN → CH01_S05_DEPART，玩家可自由探索、交谈并选择观看或跳过演出。Q01_RELIGHT保留为兼容的故事记录ID，不再代表必做任务；删除查看物品开路与旋转灯片门槛，修灯由角色协作演出。CH01_COMPLETE仅记录章节收束；两个表达选择CH01_C01_INTRO与CH01_C02_TERMS均可继续故事，不阻断衣装或可选路线。

可选短途循环：自愿选路线 → 选择事件回应/临时增益 → 返回港口；可随时退出。轮次结束或失败只清理该轮临时状态，持久故事、关系选择及衣柜保留；不要求刷材料、次数或任务。

启动 → 读取设置与内容清单 → 校验必要资源 → 主菜单 → 新游戏或验证存档 → 加载场景 → 放置角色与重建状态 → 开放输入。任一步失败都应回到可操作菜单并保留错误原因，不能进入半初始化世界。

场景转换与自动存档严格使用第4节流程 B；本节只定义场景组织。暂停菜单、对白界面和探索只能有一个主输入拥有者，演出不得绕过应用持有的输入锁。

镜头先使用固定斜俯视或有限角度切换。人物移动仍是3D坐标与3D碰撞；方向动画根据移动方向相对镜头计算。若以后允许自由旋转，必须补足多方向、遮挡和billboard阴影测试，不能只打开镜头旋转开关。

## 6 美术管线与渲染预算

### 角色与环境生产

角色建议先制作一位样板：3D建模与绑定 → 待机、步行和剧情动作 → 一致镜头下渲染多方向透明PNG → 像素与色彩修整 → 图集与动画元数据 → 引擎检查脚底锚点、轮廓和受光。手绘逐帧保留为备选；先比较两条路线的小样，再锁定四角色风格。Blender支持逐帧图像序列渲染。[9]

八方向素材量约等于角色数 × 动作数 × 方向数 × 每动作帧数。例如4角色、3动作、8方向、每动作8帧，就是768帧，尚未计表情、特写或服装变化。这是工作量示例，不是最终动画承诺。非对称发型、服饰与道具不能随意镜像。

环境以材质细节、轮廓层次、可读光影和近中远景构图达到硬约束目标；程序块模仅内部灰盒。环境在Blender保留源文件，导出GLB作为引擎输入；碰撞、可行走区域和交互锚点单独验收。资源清单记录作者、来源、许可证、商业使用和再分发限制；字体、音效与音乐同样检查。

### 必须先过的小型画面验证

AnimatedSprite3D负责逐帧播放，shaded打开后可受3D灯光影响，但表面仍是平面。法线需要匹配帧的法线图和材质同步；预烘强光会与实时光产生重复明暗。普通alpha混合有排序与投影限制；先验证Alpha Cut轮廓、场景遮挡和简化接地影。[3][4][5]

PC采用Forward+作为目标。Compatibility可作为较低画质或Web方向，但不承诺相同外观；体积雾和部分GI效果需要替代，4.6的Compatibility本身也支持Glow。先以真实GPU画面与性能决定是否保留高级效果，命令行版本检查不能替代这一步。[1]

| 第一章建议预算 | 初始上限或目标 | 调整依据 |
| --- | --- | --- |
| 画面与动画 | 1080p；人物尺寸与像素密度先做样板 | 近景表情、远景可读性和抖动测试 |
| 帧率 | 参考PC争取稳定60 fps；提供30 fps档 | 参考硬件待选，均未实测 |
| 光影 | 1个主要投影光，局部投影光先限2个 | Profiler定位后逐项增加；非引擎硬上限 |
| 内存与纹理 | 纹理图集分角色/动作，不做单张超大图 | 显存实测；2048² RGBA8基础层约16 MiB |
| 文件规模 | 源文件与导出图集优先纳入资产清单 | 重复渲染中间帧可重建，不全部提交历史 |

GDScript、JSON、文本场景用普通Git；大模型、美术源文件、图集、音频按需LFS。提交.import配置，忽略.godot/缓存、临时渲染和构建包。LFS按历史版本和下载计量，首次上传前确认账户额度与预算，不承诺无限免费。[6][7][8]

## 7 验收与回归测试

第一章试玩完成标准是自由探索和交谈可稳定体验、分支有可见回应、可保存恢复，并通过硬约束母本的真实引擎视觉门禁；角色原画获批不代表场景画质通过。下表是待执行验收，不是测试通过记录。硬件、系统、引擎补丁版本和构建号必须附在实测报告中。

| 测试面 | 具体检查 | 通过标准 |
| --- | --- | --- |
| 内容完整性 | 遍历节点、选项、事件、文本与资源引用 | 无悬空ID、无阻断流程的不可达目标；缺项给出文件位置 |
| 状态事务 | 连续点击、重复命令、重载入口、演出跳过 | 奖励与事实各提交一次；失败时整批状态不变 |
| 分支与关系 | 接受、拒绝、暂缓；撤回边界后重入场景 | 可继续主线；无越界对白；拒绝不变成错误或惩罚锁 |
| 存档与恢复 | 选择后保存；写到一半中断；坏文件与旧版本 | 原槽可恢复；迁移可追踪；设置与剧情均不丢失 |
| 移动与交互 | 角色卡角、遮挡、远距目标、过场期间交互 | 无穿墙与误触；交互对象可再次识别 |
| 画面融合 | 近中远景截图、材质、光影、景深、遮挡、镜头、角色动画与立绘 | 达到参考画面方向；人物不消失、不错误置顶，无明显黑边与阴影跳变；块模不算达标 |
| 自由玩法与衣装 | 不参加短途、失败/退出、跳过修灯、直接选所有固定皮肤、存读档及上下装切换 | 故事/衣装不被任务或轮次门槛锁定；持久状态保留；世界与立绘上衣/外套颜色同步 |
| 性能 | 冷启动、第一次特效、重复进出、最长演出 | 记录帧时间分位、卡顿、内存峰值；对照参考PC目标 |
| 操作与可访问性 | 键盘重绑定、手柄、字号、音量与阅读速度 | 可独立调音乐/音效；选项无强制计时；焦点可见 |
| 感官设置 | 关闭闪烁/震屏/景深、降低辉光与粒子 | 关键线索仍可辨；颜色不作为唯一提示 |
| 内容表现 | 全分支文本、动画、音效与失败反馈逐项复核 | 无血腥；不把身体变化做奖励；医疗叙事无剂量指令 |

### 原型需要的自动化与人工检查

设计上预留三类自动检查：静态数据验证；无界面的条件/故事/短途/衣装/关系状态测试；基于命令日志的确定性回放。人工检查覆盖像素轮廓、角色表演、对白语气、镜头晕动与长段落阅读。两者不能相互替代。

至少保留三条参考游玩路线：接受同行、保持距离、先处理工作后再回应关系。分别验证主线可达与存档恢复。关键信息应能在日志中回看；“按键完成”和“角色同意”在UI文案中明确分开。

视觉验收需真实截图或录屏，性能验收需真实GPU与导出构建；截图好看不能证明完整游戏可玩，编辑器可运行也不能证明Windows或其他目标平台导出成功。
